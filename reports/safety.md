## Decisions

**Approved launch posture (Mr. Yami Kato, relayed 2026-10-04):** teens (13-17) default to **Private / Followers-only with NO public publishing at launch**.

**Does the current code enforce this? No.** (verified, finding **S-03**, bug B-03)
- Teen account created with DOB 2011 could `PUT /api/builds/{id}/visibility {"visibility":"public"}` -> 200, then `POST /api/showcase {... "visibility":"public"}` -> 200, and an anonymous visitor saw it in Trending and fetched its files. Only the *default* is blocked (`default_visibility: public` -> 403).
- A teen could set `PUT /api/me/privacy {"profile":"public"}` -> 200 (profile was Private by default).
- A teen's profile is Private by default (cannot be followed), but once the teen sets it Public (allowed, previous bullet) any adult account can follow with no approval (`POST /api/follow/{teen}` -> 200) and the teen's follower list shows them.
- The public share page `/p/<id>` prints the teen's display name next to a public project.
- `README.md` documents "A teen can still choose Public for an individual project... (open decision)". The decision is now made, so code and README should change together. Engineering Batch 1 plans a `TEEN_PUBLIC_ENABLED` flag; it must default **off**, and be enforced in `privacy.check_level` (covers builds, edit projects and Showcase) plus `set_privacy(profile)`.
- Open policy points for Mr. Kato / counsel: should adults be able to follow teens without teen (or parent) approval; should teens be hidden from search and from `/u/<id>`; should "Followers-only" for teens require follower approval.

## Summary (top risks first)

Counts by severity (29 findings): **Critical 1 - High 5 - Medium 11 - Low 10 - Info 2.**

1. **S-01 (Critical)** Anyone on the internet, without an account, can read and overwrite the server-wide settings (`/api/settings`) and disconnect linked accounts. That lets them (a) make the server send requests to any URL they choose (SSRF, verified), and (b) change the "public base URL" that is baked into slicer deep links **and the classroom QR codes**, so students could be sent to a look-alike site and signed file tokens are sent to the attacker's host.
2. **S-03 (High)** The approved "no public publishing for teens" posture is not enforced; teens can publish Public, make their profile Public, and adults can follow them freely.
3. **S-04 (High)** The age gate is trivially bypassed and not "neutral": the error says "Accounts need age 13+", and the same browser session can immediately retry with a different birth date. Counsel should look at this against the FTC's neutral age-screen language (rank 1).
4. **S-05 (High)** Classroom join-password guessing is rate-limited per browser cookie only; clearing the cookie resets it (60 straight wrong guesses in 3 s, none rate-limited). Passwords can be 4 characters, and the class code is on a projected QR/link.
5. **S-02 / S-06 (High)** One anonymous request with a long text field freezes the whole server for ~15 s (quadratic regex in the contact-info filter on an unbounded field); and the OAuth callback page reflects its `error` parameter as HTML (reflected XSS).
Also notable: no user/parent deletion or export, EXIF/GPS kept in stored uploads, structural filter bypass (a single separator defeats ~95% of list entries), and weak report abuse controls.

## PrusaSlicer AGPL-3.0 when run server-side as a CLI (issues to raise with a lawyer, not conclusions)

**Facts I could verify**
- Installed on this box: Debian package `prusa-slicer 2.9.2+dfsg-1` (`dpkg -s`); `/usr/share/doc/prusa-slicer/copyright` lists the main work as `License: AGPL-3` with bundled parts under other licences (GPL-2+, CC-BY-3.0, etc.).
- Upstream repo `LICENSE` is the GNU AGPL v3 text (fetched: https://raw.githubusercontent.com/prusa3d/PrusaSlicer/master/LICENSE). Upstream README (https://raw.githubusercontent.com/prusa3d/PrusaSlicer/master/README.md) describes a command-line interface for automation.
- ZEIM calls it with `subprocess.run([...,"--export-gcode", ...])` in `app/services/slicer.py` on an STL file and reads back the G-code and the stdout/stderr. It does not link to it, modify it, or ship it in the repo. `reports/deploy/Dockerfile` (a proposal) installs the apt package into an image.
- AGPL v3 text (same LICENSE file): section 2 says running the **unmodified** program is permitted without conditions and that **output** is covered "only if the output, given its content, constitutes a covered work"; section 13 requires that if you **modify** the Program, your modified version must prominently offer remote-network users the Corresponding Source of *your version*; conveying (distributing) copies triggers section 4-6 duties (licence text, source offer, etc.).
- FSF GPL FAQ (could not fetch gnu.org directly: HTTP 403 to both fetch tools; read through a Wayback Machine copy of https://www.gnu.org/licenses/gpl-faq.html, **snapshot date not checked**, so confirm on the live page): *output* of a program is not in general covered by the program's licence (`#GPLOutput`, `#WhatCaseIsOutputGPL`); "pipes, sockets and command-line arguments are communication mechanisms normally used between two separate programs", unless the communication is "intimate enough, exchanging complex internal data structures" (`#MereAggregation`); fork/exec of a separate program without sharing complex data structures generally yields a separate program (`#GPLPlugins`); a company running a **modified** AGPL program on a website must release those modifications to users (`#UnreleasedModsAGPL`); the network-interaction duty applies to programs "expressly designed to accept user requests and send responses over a network" (`#AGPLv3InteractingRemotely`); providing copies to contractors for off-site use is distribution (`#InternalDistribution`).

**Questions for counsel (not answers)**
1. *Section 13 when unmodified:* we only run an unmodified distro binary. Our reading of the text is that section 13 is a duty for **modified versions**, and that users interacting with ZEIM's web app are not "interacting remotely" with PrusaSlicer itself, since the CLI is not network-facing. Is counsel comfortable with that? Does anything we do (custom config, patched packaging, wrapper scripts, forks like SuperSlicer/OrcaSlicer in `CANDIDATES`) count as "modifying"?
2. *Separate program vs combined work:* we exchange only an STL in, and G-code + text log out, via command-line arguments and files. FAQ language suggests this is "separate programs". Does counsel agree for AGPL, and is ZEIM's own code therefore not affected (no AGPL obligation on ZEIM's source)? What would change that (embedding, importing its libraries, a long-running IPC protocol)?
3. *Output:* G-code embeds PrusaSlicer comments/config (e.g. "generated by PrusaSlicer") and is the "output" of the tool. FAQ/AGPL section 2 say output is generally not covered. Any notice we should still show users?
4. *Distribution:* publishing a **Docker image** (registry push, handing an image to a school/partner, a downloadable "ZEIM server") is conveying the binary: need licence text, a source offer (or Debian's source package pointer), and notices for all bundled components. Is hosting only on our own servers different from giving a customer an image or VM?
5. *Source offer logistics:* if we do convey, which offer mechanism is acceptable (link to Debian source package version 2.9.2+dfsg-1 vs ours), for how long, and what must the UI/README say?
6. *Other tools:* `CANDIDATES` also probes `superslicer` and `orca-slicer` (both are, as I recall, AGPL-licensed, **unverified**); confirm their terms before any are shipped. Also `manifold3d`, `trimesh`, three.js, fonts (DejaVu): not audited here.
7. *Brand:* "PrusaSlicer" is a trademark (rank 11); how do we name it in UI factually (we do).
8. *Process:* add a third-party-notices page and a short "Open-source components" doc owned by Engineering once counsel answers.

**What I would do differently**
- Start with a written threat model (who: anonymous visitor, student, teen, adult stranger, malicious teacher; what: PII, photos, access to a class) and derive tests from it, instead of walking route by route; I found S-01 by reading, not by a systematic "unauthenticated route inventory". - Turn my scratch scripts into pytest cases against a temp instance, so regressions are caught; today the 101 tests don't cover any of these.

- Question one assumption: severity labels assume a hosted multi-user launch. If the first release is a closed pilot behind a school network, S-01/S-02/S-05 drop in urgency but S-03/S-04/S-08 do not.
- Question another: "teen followers-only" may itself carry risk (adults following minors). I flagged it but did not resolve it; it is a product decision plus a counsel question.
- Ask Engineering earlier which items were already planned (Batch 1) to avoid duplicating effort; I saw their plan only near the end.
