# mslicer vs DragonFruit, measured

This is a bench of two resin slicers for TorchC0. It does not change how ZEIM slices, and it does not merge either engine into `app/`. Nothing in this report was printed on a machine.

**Recommendation.** Keep mslicer as the program TorchC0 runs for `.goo` and `.ctb`. On this machine DragonFruit's process was faster on every input, and both engines' masks matched an independent rectangle exactly. The stored images are still not the same: DragonFruit's picture is flipped top to bottom relative to mslicer's, and that flip has not been checked against a Jupiter panel. Switching on the strength of the timer alone would change the orientation of every part. Confidence is medium: the timings and the mask math are repeatable; the printer is not.

## What was compared

Same solids, same plates, same slice settings. Supports off. Anti-aliasing off. No extra rotation. Catalog mirror flags were not applied.

Settings are TorchC0's standard preset: 0.05 mm layers, 2.5 s exposure, 30 s bottom exposure, 5 bottom layers, 6 mm lift at 65 mm/min, retract speed equal to lift speed.

Plates are the Elegoo sizes already in `app/core/lumen_plates.json` (pixel pitch from df-plugin-elegoo, build size = pixels times pitch):

| Plate | Pixels | Bed (mm) | File written for the timed runs | Catalog native file |
|---|---|---|---|---|
| ELEGOO Jupiter | 5448 x 3064 | 277.848 x 156.264 x 300 | unencrypted CTB v4 | CTB v5 |
| ELEGOO Saturn 2 | 7680 x 4320 | 218.88 x 123.12 x 250 | unencrypted CTB v4 | CTB v5enc |
| ELEGOO Mars 5 | 4098 x 2560 | 143.43 x 89.6 x 165 | GOO | GOO |

v4 was the timed container so UVtools 7.1.2 could read both writers. Native CTB v5 / v5enc were a separate one-file check, below. mslicer's Mars 5 preset in its own GUI table is 150 mm tall; this bench passed 165 mm, the ZEIM plate.

Meshes, generated by `fixtures.py` (the repo had no mesh over 900k triangles):

| Mesh | Triangles | Size (mm) | Layers at 0.05 mm |
|---|---|---|---|
| Box | 12 | 20 x 16 x 12, centred, on the bed | 240 |
| Asymmetric | 24 | 30 x 20 x 4 slab, plus a 10 x 8 tower on the +X +Y corner up to z = 12 | 240 |
| Sculpt | 906300 | height field, 48 x 40 x 20 | 400 |

DragonFruit's raster origin is the centre of the plate. mslicer's `--placed` origin is the minimum corner. Each engine got the same solid in its own coordinates, not the same STL bytes. Both sample a layer at `(index + 0.5) * layer_height`.

Host: 4 vCPU, `lscpu` model string `Intel(R) Xeon(R) Processor` (a generic hypervisor name). Measured 2026-11-09. Every number below is the median of 3 runs unless a row says otherwise. Cold means the slicer binary and its shared libraries were dropped from the page cache with `posix_fadvise` before the run. Warm means they were left in cache. This is not a reboot. Raw records, including every run, are in `results/raw.json`.

## Which process was faster

Wall clock is the whole process: start, read the STL, slice, write the file, exit. That is what TorchC0 pays, because it spawns a slicer per job. "Engine" is the timer the program itself prints (mslicer's `Finished in`, DragonFruit's `wall_s`), which starts after the mesh is loaded.

| Case | mslicer wall cold / warm | DragonFruit wall cold / warm | mslicer engine warm | DragonFruit engine warm | Warm RSS |
|---|---|---|---|---|---|
| Jupiter box | 17.8 / 10.9 ms | 17.1 / 8.6 ms | 8.7 ms | 6.3 ms | 10.3 / 15.3 MB |
| Jupiter asymmetric | 14.8 / 10.7 ms | 13.4 / 8.8 ms | 7.8 ms | 6.7 ms | 9.7 / 14.8 MB |
| Jupiter sculpt | 355 / 331 ms | 217 / 183 ms | 71.4 ms | 93.0 ms | 63.7 / 161 MB |
| Saturn 2 box | 19.7 / 17.2 ms | 15.2 / 12.9 ms | 14.7 ms | 10.0 ms | 14.9 / 16.3 MB |
| Saturn 2 asymmetric | 19.6 / 14.9 ms | 13.4 / 8.7 ms | 13.7 ms | 7.0 ms | 12.8 / 15.7 MB |
| Saturn 2 sculpt | 373 / 350 ms | 210 / 192 ms | 84.5 ms | 100.4 ms | 75.8 / 161 MB |
| Mars 5 box | 17.1 / 12.9 ms | 10.8 / 8.5 ms | 10.6 ms | 6.7 ms | 12.7 / 7.7 MB |
| Mars 5 asymmetric | 16.7 / 10.7 ms | 11.1 / 6.5 ms | 8.4 ms | 6.2 ms | 11.3 / 7.6 MB |
| Mars 5 sculpt | 367 / 335 ms | 217 / 177 ms | 73.6 ms | 90.3 ms | 73.1 / 157 MB |

DragonFruit's process was faster on all nine cases, cold and warm. On the sculpt the margin is about 1.8x (Jupiter warm 331 ms vs 183 ms). It is not 20x. mslicer's README says it is often 20x to 120x faster than other slicers. That did not show up against this DragonFruit build on these parts.

The engine's own timer tells a narrower story. On the box and the L, DragonFruit's timer was a few milliseconds faster. On the unscaled sculpt, mslicer's timer was faster (Jupiter 71 ms vs 93 ms, Saturn 2 85 ms vs 100 ms, Mars 5 74 ms vs 90 ms). DragonFruit still won the process clock there because less time was spent outside that timer.

RSS on the sculpt was about 2.2x to 2.5x higher for DragonFruit (about 160 MB vs 64 to 76 MB). On the small Mars 5 parts DragonFruit used less.

Two extra checks, not in the table above:

- A 260 x 140 x 0.2 mm rectangle, most of the Jupiter bed, 4 layers, 3 cold and 3 warm. Both finished in 4 to 7 ms. A big simple rectangle is cheap for both. Median warm wall was 6 ms (mslicer) and 4 ms (DragonFruit).
- The same 906300-triangle sculpt scaled in XY to 240 x 140 mm, still 20 mm tall, Jupiter, 3 runs with the process already warm. Median wall 382 ms (mslicer) vs 194 ms (DragonFruit). Median engine time 118 ms vs 110 ms. Peak RSS about 97 MB vs 162 MB. Filling most of the bed did not change the ordering and did not make either engine slow. These slicers are spending their time on the triangles, not on walking every pixel of a 16-megapixel plate, at least for this mesh.

Plate pixel count barely moved the sculpt times (Jupiter 16.7 Mpx, Saturn 2 33.2 Mpx, Mars 5 10.5 Mpx, all about 0.18 to 0.35 s). A part with both a huge triangle count and a full-bed, high-frequency surface was not run.

## Which output is more correct

UVtools 7.1.2 opened every timed file. Layer count, resolution, layer height, exposure, bottom exposure, and bottom layer count matched the request on every file. The first layer was not empty and the last layer was not empty. Both engines reported the input triangle count back (12, 24, and 906300). Nothing was dropped.

Masks were checked against a rectangle drawn from each engine's own published mapping, using the same half-open pixel rule both use (`ceil(edge - 0.5)`). Sampled layers: box at 0, mid, and last; the L at the slab (z = 0.025 and 2.025) and the tower (z = 8.025 and 11.975). On Jupiter, Saturn 2, and Mars 5, both engines matched that rectangle with **zero** differing pixels, and the pixels were only 0 or 255. There is no hole, no missing corner, and no dropped bed layer in these fixtures.

They do not match each other, for two reasons that the rectangle test separates:

1. **Y is stored the other way up.** DragonFruit maps world +Y toward image row 0 (its `geometry.rs` flips Y). mslicer writes the low-Y scanline first, and UVtools keeps that order. On the tower, comparing the files as stored gives IoU 0. After flipping DragonFruit's image in Y, IoU is 0.987 on Jupiter and 0.996 on Saturn 2, and the remaining pixels are a one-pixel edge. The centred slab hides this, because flipping it changes nothing. A printer would show one of these as the front of the part. This bench cannot say which. Saturn 2 and Mars 5 are marked `mirror_y` in the catalog; this run did not apply that flag.

2. **The plate is scaled by `resolution` or by `resolution - 1`.** mslicer maps the bed onto `0 .. width`. DragonFruit maps it onto `0 .. width - 1`. On the Jupiter box that is the whole disagreement: 705 pixels, IoU 0.994, all of it on the boundary. Saturn 2 box: 1263 pixels, IoU 0.997. Mars 5 box: 1029 pixels, IoU 0.996. The sculpt, after the Y flip, is the same kind of edge gap (Jupiter mid-layer IoU 0.993, 1673 pixels). The top cap of the sculpt is only a few hundred pixels, so the same edge is a larger fraction of that one layer (IoU 0.89 on Jupiter after the flip).

File headers are where mslicer's output matched the request more directly:

| | mslicer, timed run | DragonFruit, timed run | DragonFruit, one follow-up file |
|---|---|---|---|
| CTB machine Z | the plate (300 / 250) | the part height (12 or 20) | 300, once `printer.buildVolumeMm.height` and `ctb.bedSizeZ` were in the metadata |
| GOO machine Z | 165 | 220, the encoder's default | 165, with `printer.buildVolumeMm.height` |
| GOO anti-alias field | 0 | 8, the encoder's default, while the pixels stayed binary | 1, with `goo.antiAliasingLevel` |
| GOO version bytes | `V3.0` | `V1.2` | still `V1.2` (UVtools "Version" 12) |

`slice run` has no build-height flag. The CTB and GOO encoders take the height from metadata, and the timed command did not pass it. The follow-up files show those two header fields can be set without patching DragonFruit. The GOO version byte was not changed by that metadata. Both GOO files decoded in UVtools and both matched the rectangle, so the version byte did not stop a read. It is still a different container revision than mslicer wrote. Whether a Mars 5 accepts `V1.2` was not tested.

Output size, timed files: DragonFruit's CTB is larger (Jupiter box 687669 vs 483875 bytes, sculpt 2286343 vs 2079574 bytes). Mars 5 GOO is almost the same size (box 653408 vs 654368 bytes).

Native containers, Jupiter box, one file each, UVtools opened all three:

| Writer | Asked for | Magic | UVtools version | Bytes | Machine Z |
|---|---|---|---|---|---|
| mslicer `--ctb v5` | its encrypted v5 | `0x12FD0107` | 5 | 479765 | 300 |
| DragonFruit `--format-version v5` | v5 | `0x12FD0106`, version byte 5 | 5 | 687753 | 12 |
| DragonFruit `--format-version v5enc` | encrypted v5 | `0x12FD0107` | 5 | 683577 | 12 |

A `.lumen` file from DragonFruit starts with `LUMN` and is 15 KB. UVtools was not asked to read it, and the layer images inside it were not compared. mslicer does not write `.lumen`.

## Feature coverage

| | mslicer v0.10.1 CLI (`slicer`) | DragonFruit `dev` CLI (`dragonfruit-cli` 2.1.1) |
|---|---|---|
| What actually sliced | `slicer` raster path, then its goo/ctb writer. The GUI was not built. | `slice run` calls `dragonfruit-slicing-engine` 3.3.3 `slice_with_progress_v3_to_path`, then the plugin encoder. The Next.js UI, Tauri shell, island tools, and support authoring were not run. |
| Formats this binary registers | `.goo`, `.ctb` (unencrypted v4, or mslicer's own encrypted v5), `.nanodlp`. The README also lists SVG. | `.ctb` v4 / v5 / v5enc, `.goo`, `.lumen`, `.nanodlp`, `.aff`, `.azf`. The Anycubic plugin's JSON lists many more suffixes; the CLI's format list is these six. |
| Supports | Not generated. The CLI has no support pass. Upstream points at Runebrace. | Not generated. Support trees live in the TypeScript scene path, which this bench did not run. A bare STL is the solid only. |
| Anti-aliasing | `--supersample`. These runs used 1. The flag is cube-rooted before use (`cbrt` in `args.rs`), so 8 does not mean 8x. | Off / 2x / 4x / 8x, plus blur, 3D AA, and dither. These runs forced Off, blur radius 0, and z-blend 0. A default blur radius of 1 leaves gray edge pixels even when the level is Off; that was measured and then turned off. |
| Mirror | No CLI flag. ZEIM already records catalog mirror and does not write it. | `--mirror-x` and `--mirror-y`. On the Jupiter tower they moved the solid onto the mirrored rectangle and kept the same pixel count (30772). |
| Printer list | 100 presets in 17 brands in the GUI table. The CLI ignores that table and takes resolution and size on the command line, so any plate. 5 presets are marked validated. | Elegoo plugin: 3 Jupiter, 10 Mars, 7 Saturn, plus Anycubic (27), Athena (6), Uniformation (4). Geometry still has to be passed into `slice run`; the CLI does not load a preset by name. |

## How they were built

DragonFruit was not copied into this repo. The binary stays outside it.

- Repository: https://github.com/Open-Resin-Alliance/DragonFruit
- Branch `dev`, commit `97596a55882cb139bbcf96bb98b211f82ae4c5f0` (2026-11-08, "Kitchen sink: delete plate 1, plate name selection, Cmd key release, Linux tauri:dev").
- Tag `v0.3.1` (`0346fcf743a80b5cea603de2c9c023ef879878e2`, 2026-11-03) is an ancestor. `dev` is 107 commits ahead of it. `main` has diverged and is not this slicer.
- Licence of the application: AGPL-3.0-or-later. The `plugins/` submodules are MIT and are compiled into this binary.
- Rust: `rust-toolchain.toml` asks for 1.97.0. Built with rustc 1.97.0 (`2d8144b78`, 2026-07-07).
- `node scripts/generate-plugin-registry.mjs` on Node v22.23.4. `package.json` asks for Node `>=24.22.2 <25`. The generator uses Node builtins only, and it succeeded without `npm install`. That generated `generated_plugin_encoders.rs`, which `#[path]`-includes the plugin encoders.
- `cargo build --release --bin dragonfruit-cli` in `rust/dragonfruit-cli`. About 77 s. Binary version 2.1.1.

Submodules checked out with that commit: ctb `44861de1`, elegoo `be59b159` (the same commit ZEIM already cites for plate geometry), lumen `109d7d44`, anycubic `cb7b9c92`, athena is in the main tree, plus the import and network plugins that do not encode slices.

mslicer is the vendored tree at `third_party/mslicer`: upstream v0.10.1, commit `2d639519eedf4269a341fb6d5508901e06d99d48`, plus the ZEIM changes in `ZEIM-CHANGES.md` (`--ctb`, `--placed`, mid-slab sample). `cargo build --release -p slicer --bin slicer` with the same rustc. The GUI crate was not built. Licence GPL-3.0 only.

UVtools 7.1.2 linux-x64 (`UVtoolsCmd`) read the files. It is not vendored.

## AGPL, if ZEIM ran this binary

This is the same kind of note as `docs/licensing.md`. It is not legal advice. It does not relicense ZEIM, and this pull request does not adopt DragonFruit.

DragonFruit's application is AGPL-3.0-or-later. The binary this bench ran is that program with the MIT plugin encoders compiled in. The whole binary is the AGPL program. The MIT plugins on their own are a different question; this bench did not use them apart from the AGPL engine. `df-plugin-ctb` contains AES material. ZEIM's current licensing note refuses to copy that plugin into the tree. Running it inside the separate DragonFruit process is not a copy into `app/` or `third_party/`. This pull request does not add that source.

If ZEIM ran an **unmodified** `dragonfruit-cli` the way it runs PrusaSlicer and mslicer (a separate process, no linking, no pasted source):

- Shipping the binary means shipping the corresponding source of that program. For an unmodified build, that source is this commit, including the plugin submodules the binary was compiled with and the `generate-plugin-registry` step that produces the encoder file. A credits line of the kind ZEIM already uses for PrusaSlicer (name, AGPL-3.0-or-later, unmodified, link to that commit) is the pattern already written down. ZEIM's own code stays ZEIM's.
- AGPL section 13's extra network duty is written as applying **if you modify the Program**. An unmodified binary does not, on that text, require ZEIM to publish ZEIM. That is the same shape as the PrusaSlicer decision already in `docs/licensing.md`.
- "Or any later version" belongs to DragonFruit. It is not a licence for ZEIM.

If ZEIM **modified** DragonFruit (a patched CLI, a fork, or a committed edit to the engine) and people on the network triggered that modified program through ZEIM, section 13 would require offering those users the corresponding source of that modified version, at no charge, from a network server. Linking the engine into `app/`, or copying its source into the Python tree, would be a combined work. ZEIM's PrusaSlicer rule already forbids that, and it should be the rule here too. Do not relicense ZEIM to do it.

mslicer, if ZEIM keeps shipping it, stays GPL-3.0 only. Adopting DragonFruit would not erase that, and it would not relicense either program into the other.

## What is not verified

- No printer, no resin, no exposure test. File headers and masks are not a print.
- Which Y orientation a Jupiter, Saturn 2, or Mars 5 actually exposes.
- Whether a Mars 5 accepts GOO `V1.2`, or a Jupiter accepts DragonFruit's v5 / v5enc as firmware rather than as a file UVtools can open.
- Anti-aliasing quality. Supports. A mesh that is both very large and full of fine surface detail across the whole bed.
- The `.lumen` bytes past the `LUMN` magic.
- Any machine other than this 4-vCPU VM.
